# HDFS and Hive Metastore checks

Reads of Iceberg tables that live in a Hive Metastore, with their data on
HDFS, through `duckdb-hdfs` (the `hdfs://` file system and the
`hive_metastore` catalog, both on a JVM inside the backend).

The stand is the ADH 4.3 demo compose project at `~/ws/adh-show`, cut down to
seven services and started under its own compose project name. Nothing from
that repository is copied here: `ADH_SHOW_DIR` points at it, and
`docker-compose.hdfs.yml` only overrides what a client on the host needs.

    ADH_SHOW_DIR=~/ws/adh-show ./up.sh      # start, seed, print the host setup
    ./run.sh                                # the checks
    ./down.sh                               # remove the project and its volumes

## What runs, and what does not

`kdc`, `openbao`, `pg`, `namenode`, `datanode`, `hdfs-init`, `metastore`.
YARN, HiveServer2, Ozone, Trino, Impala, Spark's servers, Hue, Knox, Ranger
and the notebooks stay down. `openbao` is there because the stand's
entrypoints block until it hands out a token, not because we use it.

Security stays as the stand ships it: Kerberos, with RPC and data transfer
encrypted, and SASL on the metastore. That is what an ADH cluster looks like,
and it is the part most likely to break, so the tests run against it rather
than a relaxed copy. The one thing taken out is the NameNode's Ranger
authorizer, since Ranger is not among the services we start
(`GG_HDFS_KEEP_RANGER=1` keeps it).

## Before the first run

Nothing here needs root.

* **Docker Compose v2.** The stand's compose file is v2 syntax, and v1 cannot
  read it (it fails on a `$(hostname -f)` healthcheck). Without a package
  manager, take the binary out of an image:

      docker create --name c docker/compose-bin:latest /docker-compose
      docker cp c:/docker-compose ~/.docker/cli-plugins/docker-compose
      docker rm c && chmod +x ~/.docker/cli-plugins/docker-compose

* **The `adh-base` image**, about 8 GB, built from the stand over the VPN.
  Compose can build it, and so can docker alone:

      docker build -t adh-base:4.3.0 -f image/Dockerfile \
          --add-host downloads.adsw.io:$ADSW_IP .

* **A build with HDFS**: `duckdb/build.sh` run with `DUCKDB_HDFS_DIR` (see its
  header).

`up.sh` takes care of the rest: it writes the hosts file the backend's JVM
resolves the stand's names from (`-Djdk.net.hosts.file`, which is why
`/etc/hosts` is left alone -- the Iceberg metadata names
`hdfs://nn.adh.local:8020/...` absolutely, so the names have to resolve
somewhere), copies the stand's `krb5.conf` for the JVM to read, and gets a
ticket by running `kinit` inside the KDC container and copying the cache out,
so the host needs no Kerberos tools either. The cache is a file owned by the
OS user running the server, mode 0600, which is what `duckdb-hdfs` requires:
it reads a ticket cache and cannot log in from a keytab. The ticket lasts a
day, and nothing renews it.

## The data

`up.sh` registers the stand's shipped `demo_hdfs` database (`sales`,
`web_events`, `customers`, `products`, `regions` -- all Iceberg) and creates a
`gg` database of its own with two tables whose shapes the checks need:

* `gg.events` -- partitioned by day, written in two snapshots, copy-on-write.
  A reader that stops at the first metadata file loses the second snapshot's
  rows, so the counts catch it.
* `gg.events_mor` -- the same rows with a merge-on-read `DELETE`, so the table
  carries positional delete files. A reader that lists data files and reads
  them directly returns the deleted rows; that is the case file-level sharding
  must refuse to take.

`expected_ref.txt` holds the aggregates Spark computed while seeding, which is
what `run.sh` compares against.

## Known wart

With a missing or expired ticket the error is DuckDB's `Table ... does not
exist because schema ... does not exist`, not an authentication failure: the
ATTACH itself never contacts the metastore, and `duckdb-hdfs` swallows the
catalog load failure and serves an empty catalog. The query fails and the
backend lives; the message misleads. Fixing it means changing `duckdb-hdfs`.
